# VT Rank Tracker --- техническая документация

**Версия документа:** 11 ноября 2026 г.\
**Статус:** рабочая документация; часть файлов и функций описана по
согласованной архитектуре и доступным исходным фрагментам, а не по
полному экспорту текущего Apps Script проекта.

## 1. Назначение

Проект Google Sheets / Apps Script автоматизирует таблицу результатов
Kovaak's / Voltaic для листов `Novice`, `Intermediate` и `Advanced`.

Основные подсистемы:

-   фильтрация сценариев по Dots и TOP;
-   сохранение автоматического состояния фильтров (FilterState);
-   сохранение ручных исключений (ManualState);
-   сортировка блоков сценариев;
-   Rank Scroller --- управление видимыми колонками рангов по Energy;
-   обработка изменений и пользовательских операций через триггеры;
-   диагностика производительности и блокировки операций.

### Принципы разделения

-   Оркестраторы управляют последовательностью действий.
-   Engine-модули связывают чтение данных, вычисления и применение
    результата.
-   Calculator-модули содержат чистые вычисления без Google Sheets API.
-   State-модули отвечают за сохранение и проверку состояния.
-   Visibility-модули применяют рассчитанную видимость.
-   Config-файлы содержат настройки, а не бизнес-логику.

## 4. Фильтрация и состояния

### FilterState и ManualState

Это два независимых слоя:

1.  **FilterState** хранит результат автоматических фильтров Dots + TOP.
2.  **ManualState** хранит постоянные ручные исключения.

Итоговая физическая видимость:

`FilterState AND NOT ManualState`

Строка отображается, если она проходит автоматические фильтры и не
является ручным исключением.

### FilterState

Состояние проверяется по метаданным, размерам и длине массива видимости.
Если состояние валидно и соответствует текущей структуре листа, оно
может быть повторно использовано. Запись пропускается, если значения не
изменились.

По runtime-журналам 11 ноября 2026 года FilterState был валиден на всех
трёх листах; при неизменной видимости запись состояния пропускалась.

### ManualState

ManualState хранит ключи содержимого строк, а не номера строк, поэтому
исключения сохраняются при сортировке.

`getManualRecordKey_(row)` формирует ключ по C:L; значения Date
преобразуются в ISO-строку. Для одинаковых строк используются частотные
счётчики (`Map`), чтобы совпадающие записи не схлопывались.

Колонки ManualState:

  Лист           Колонки
  -------------- ---------
  Novice         J:K
  Intermediate   M:N
  Advanced       P:Q

Режимы синхронизации: - `Manual` --- сохранение командой
`Save Manual Hidden Rows`; - `Automatic` --- синхронизация при следующем
запуске фильтров.

`onEdit` не может надёжно отследить ручное скрытие/отображение строки,
поэтому мгновенная синхронизация при hide/show не выполняется.

## 5. Сортировка

`Sorting.gs` использует пакетный подход:

1.  считывает названия сценариев;
2.  считывает диапазон сортируемых данных;
3.  проверяет порядок внутри блоков в памяти;
4.  пропускает уже отсортированные блоки;
5.  вызывает `Range.sort()` только для блоков, где найдено нарушение;
6.  записывает диагностические показатели.

Поддерживаемые режимы: `scoreDesc`, `scoreAsc`, `dots`.

Причины диагностики: - `EMPTY_DOTS`; - `NON_ASCII_DOTS`; -
`INVALID_SCORE`; - `UNSORTED_SCORE_DESC`; - `UNSORTED_SCORE_ASC`; -
`UNSORTED_DOTS`; - `ALREADY_SORTED`.

Сравнение Dots в JavaScript может отличаться от локаль-зависимой
сортировки Sheets. `Range.sort()` остаётся авторитетной операцией.
Пустая Dots-строка должна находиться внизу блока; `EMPTY_DOTS` для
пустой строки выше последней позиции --- ожидаемая диагностика.

**Подтверждённый тест:** первый запуск обнаружил несортированный блок
`VT Pasu Intermediate` и `EMPTY_DOTS` в `VT AvasiveTS Intermediate`.
После сортировки Pasu следующий запуск пропустил этот блок; осталась
только ожидаемая диагностика пустой Dots-строки AvasiveTS.

## 6. Rank Scroller

Принятое разделение:

-   `RankScroller.gs` --- оркестрация;
-   `RankScrollerEngine.gs` --- обработка одного листа;
-   `RankScrollerCalculator.gs` --- чистые вычисления;
-   `RankScrollerVisibility.gs` --- видимость колонок;
-   `RankScrollerState.gs` --- Script Properties и dirty-флаги.

Dirty-state позволяет не пересчитывать листы без изменений. Список
обрабатываемых листов получается из
`Object.keys(CONFIG.rankScroller.sheets)`. State-модуль читает свойства,
сохраняет только изменения, помечает один/все листы dirty и сбрасывает
dirty после обработки.

`calculateRankScrollerTargetColumn_()` не обращается к Sheets API.
Проверенный пример: Energy 564, пороги 100...1600, стартовая колонка 14,
всего 16 колонок, видимых 4 --- целевая колонка 18.

## 7. Общие утилиты

В предоставленном блоке присутствуют:

-   `columnToLetter_(column)` --- номер столбца в буквы;
-   `columnToIndex_(letters)` --- буквы в номер;
-   `columnLetterToIndex(letter)` --- wrapper для старого имени;
-   `getColumnDataRange_(column, firstRow)` --- диапазон столбца;
-   `getCellAddress_(row, column)` --- A1-адрес;
-   `getA1Range_({...})` --- A1-диапазон;
-   `getTargetSheet(sheetName, spreadsheet)` --- выбор рабочего листа;
-   `logFilterTiming(label, startedAt)` --- время выполнения;
-   `rangeIntersectsCell(range, a1Notation)` --- проверка пересечения;
-   `getRankScrollerOptions_(spreadsheet)` --- чтение Options.

`getTargetSheet()` использует активный лист, если он входит в
`RANK_TRACKED_SHEETS`; иначе берёт `CONFIG.sheetName`. Если Spreadsheet
передан аргументом, повторный вызов `getActiveSpreadsheet()` не
требуется.

## 9. Производительность

В проекте используются: - Performance Tracer с событиями START / STEP /
END / SUMMARY; - локальные таймеры фильтрации; - диагностика
сортировки; - пакетное чтение диапазонов; - пропуск записи состояния без
изменений; - Lock Manager для защиты критических операций.

В `Operations.gs` согласовано оставить только `operationPerfStep_()` и
`operationPerfEnd_()`.

Единичные задержки Google Sheets API следует отличать от медленной
логики алгоритма. В журналах встречались отдельные долгие чтения при
последующих успешных запусках; один такой замер сам по себе не
доказывает регрессию.

## 11. Правила дальнейших изменений

1.  Перед изменением функции проверять все её вызовы и потребителей.
2.  Сохранять публичные имена функций и структуру `CONFIG`, если
    изменение интерфейса отдельно не согласовано.
3.  Не переносить функции только ради формального разделения файлов.
4.  Не дублировать источники истины для списка листов и координат.
5.  Держать чистые вычисления отдельно от Spreadsheet API.
6.  Читать диапазоны пакетно и не записывать состояние, если оно не
    изменилось.
7.  Различать фильтрационное и ручное скрытие.
8.  Для ManualState использовать ключи записей, а не номера строк.
9.  Не менять порядок массива `getRankScrollerOptions_()` без аудита
    потребителей.
10. После существенных изменений выполнять адресный и общий
    регрессионный тест.
11. Не считать код обновлённым в таблице, пока пользователь не внесёт
    изменения и не подтвердит runtime-результат.

Доступный файл `FilterVisibility.gs` содержит следующие функции:

### 13.8. 06_CustomFunctions.gs

Доступный файл содержит пользовательские функции Google Sheets:

| Функция | Назначение | Зависимости / ограничения |
|---|---|---|
| `energy(score, requirements)` | Интерполирует Energy по порогам Score | Читает значения рангов из активного листа, строка 2, начиная с колонки J; вызывает `interpolate()` |
| `interpolate(score, currentThreshold, nextThreshold, currentRank, nextRank)` | Линейная интерполяция между двумя точками | Чистое арифметическое вычисление |
| `getRank(energy, userScores, energyRequirements, scoreThresholds, headers, showCompleteRank)` | Определяет обычный / Complete rank | Преобразует входные массивы в плоские; сравнивает Energy и индивидуальные Score с порогами |
| `matchColor(energyVal, firstThreshold, lastThreshold, divisor, colorList, fallbackColor)` | Выбирает цвет по значению Energy | Нормализует двумерный список цветов в одномерный и ограничивает индекс границами |
| `showNextRank(value, rankRange)` | Возвращает ближайший следующий порог ранга | Если значение выше всех порогов, возвращает последний порог |

**Важная особенность `energy()`:** функция зависит от активного листа и
читает диапазон `getRange(2, 10, 1, reqs.length)`. Это означает, что
перенос функции в модуль с иной логикой выбора листа или изменение
активного листа может изменить результат. Перед изменением нужно
проверить формулы, которые вызывают `energy()`.

## 14. Карта зависимостей и потоки выполнения

### 14.1. Основной поток фильтрации

```text
Пользователь / onEdit / меню
          |
          v
   FilterOperations / операции
          |
          v
      applyFilters()
          |
          +--> FilterData: чтение входных данных, TOP, last row
          |
          +--> FilterState: чтение и проверка предыдущего состояния
          |
          +--> ManualState: загрузка ручных ключей / исключений
          |
          +--> FilterEngine: расчёт Dots + TOP
          |
          +--> FilterVisibility: расчёт физической видимости,
          |                      применение изменений,
          |                      сохранение FilterState
          |
          +--> RowVisibility: групповые show/hide операций
          |
          +--> Performance Tracer: этапы и итоговая диагностика
```

Схема отражает известные границы модулей. Конкретный порядок отдельных
вызовов внутри `applyFilters()` следует сверять с полной текущей
реализацией.

### 14.2. Основной поток Rank Scroller

```text
handleEdit / меню / комплексная операция
          |
          v
    runRankScroller()
          |
          +--> Lock Manager / Performance Tracer
          |
          v
     rankScroller()
          |
          +--> CONFIG.rankScroller.sheets
          +--> Options (A5, A10, A11)
          +--> RankScrollerState (Script Properties / dirty flags)
          |
          +--> RankScrollerEngine (чтение и обработка листа)
          |         |
          |         +--> RankScrollerCalculator (чистый расчёт)
          |         +--> RankScrollerVisibility (show/hide колонок)
          |
          +--> сохранение изменённых Script Properties
```

Ключевой принцип: dirty-флаг сбрасывается только после успешной
обработки листа; неизменённые листы пропускаются. Это позволяет не
выполнять одинаковые операции при каждом запуске.

### 14.3. Поток сортировки

```text
applyFilters() / ручная команда сортировки
          |
          v
 sortScenarioBlocks()
          |
          +--> чтение C и C:L
          +--> группировка последовательных строк по сценарию
          +--> inspectScenarioBlockOrder_() для каждого блока
          +--> Range.sort() только для блоков с нарушением
          +--> диагностический результат / Performance Tracer
```

### 14.4. Поток событий

```text
onOpen() ----------------------> создание пользовательских меню

installable onEdit
      |
      v
  handleEdit(e)
      |
      +--> RankReqs -----------> markAllRankSheetsDirty()
      |                          -> runRankScroller(false)
      |
      +--> Options / Auto Sort -> markAllRankSheetsDirty()
      |                          -> refreshAllFiltersAndRanks()
      |
      +--> Options / Hide Empty -> refreshAllFiltersOnly()
      |
      +--> Options / Rank opts -> markAllRankSheetsDirty()
      |                          -> runRankScroller(false)
      |
      +--> игровые листы ------> адресная проверка изменённых ячеек
                                 -> фильтры / сортировка / Rank Scroller
```

Это описание ветвления по предоставленному `Triggers.gs`; полный список
условий игровых листов и точные точки входа должны оставаться в исходнике
источником истины.

### 15.1. Дублирование списка листов

Сейчас список игровых листов существует в двух формах:

- `RANK_TRACKED_SHEETS = ['Novice', 'Intermediate', 'Advanced']`;
- ключи `CONFIG.rankScroller.sheets`.

Первый используется `getTargetSheet()` и `handleEdit()`, второй —
Rank Scroller. Это подтверждённое дублирование. Предлагаемое направление
после полного поиска потребителей: получать список игровых листов из
одного источника, например через helper над
`Object.keys(CONFIG.rankScroller.sheets)`. Само изменение пока не
выполнено: сначала нужно проверить все ссылки на `RANK_TRACKED_SHEETS`
и убедиться, что конфигурация доступна к моменту вызова helper.

### 15.2. Смещения сортировки

В текущем `sortScenarioBlocks()` индексы вычисляются от абсолютных
колонок: E относительно C даёт `2`, I относительно C даёт `6`.
В `CONFIG` одновременно присутствуют `sortScoreOffset: 3` и
`sortDotsOffset: 7`. Эти значения не совпадают с используемыми
zero-based индексами массива C:L. Поскольку в предоставленном коде
Sorting.gs эти CONFIG-поля не читаются, они выглядят как устаревшие
или иначе трактуемые настройки. Не исправлять и не удалять до поиска
по всему проекту и проверки возможных потребителей.

## 17. Дополнительные находки по историческим снимкам исходников

При поиске по доступным текстовым снимкам обнаружены функции, которых
нет в последнем предоставленном блоке `Utils.gs` / `Triggers.gs`, но
которые присутствуют в более раннем объединённом исходнике от 10 ноября.
Их нельзя автоматически считать частью текущей версии.

| Функция | Что подтверждает исторический снимок | Что проверить |
|---|---|---|
| `getOptionBoolean_(optionName)` | Берёт `CONFIG.options[optionName]`, открывает `CONFIG.optionsSheetName`, читает указанную ячейку и возвращает `getValue() === true` | Существует ли функция в текущем проекте; не заменена ли пакетным чтением Options |
| `isAutoSortEnabled()` | Вызывает `getOptionBoolean_('autoSort')` | Остались ли вызовы после перехода на централизованное чтение настроек |
| `runManualSortOperation_(...)` | Присутствует в историческом объединённом фрагменте | Проверить полную реализацию, точки входа меню и возможное пересечение с `SortOperations.gs` |

В том же историческом файле присутствуют версии `getTopN()`,
`getLastScenarioRow()`, `getLastScenarioRowFromData()`, `applyFilters()`,
`showAllDataRows()`, `updateRowsVisibility()`, `showRowsInGroups()` и
`hideRowsInGroups()`. Эти функции уже отражены в архитектурном справочнике,
но исторический файл объединяет код нескольких модулей и не должен
использоваться как источник текущей структуры файлов.

### 17.1. Результат статического поиска по доступным файлам

Поиск выполнен по автоматически смонтированным `.txt`, `.md` и `.gs`
файлам в текущей рабочей папке. В доступных исходных снимках не найдено
надёжного подтверждения использования следующих полей конфигурации:

- `clearScoreCol`, `clearDotsStartCol`, `clearDotsEndCol`;
- `sortScoreAscending`, `sortDotsAscending`;
- `sortScoreOffset`, `sortDotsOffset`;
- `perfModeCell`, `perfDefaultMode`.

Это не доказывает отсутствие потребителей в Apps Script: часть файлов
проекта отсутствует среди доступных снимков, а некоторые снимки могут
быть устаревшими. Поэтому поля остаются в категории «не подтверждено»,
а не «не используется».

`CONFIG.options` имеет дополнительный исторический потребитель —
`getOptionBoolean_()`. В более новом `handleEdit()` координаты настроек
также используются напрямую. До решения о сохранении или удалении
`getOptionBoolean_()` необходимо проверить актуальные вызовы и
сопоставить старый поячейковый доступ с текущей пакетной схемой чтения.

## 18. Следующий практический шаг

Для завершения инвентаризации нужен актуальный экспорт недостающих
модулей, в первую очередь:

1. `FilterOperations.gs` и `SortOperations.gs`;
2. актуальный `Operations.gs` и меню/публичные точки входа;

### 19.1. FilterOperations.gs

| Функция | Назначение | Основные зависимости |
|---|---|---|
| `resetFilters()` | Сбрасывает I1:J1 активного игрового листа, применяет фильтры и обновляет Rank Scroller | `withProjectLock`, `getTargetSheet`, `getRankScrollerOptions_`, `applyFilters`, `rankScroller`, `operationPerfStep_` |
| `refreshFiltersAndRanks(...)` | Обновляет фильтры одного листа и опционально Rank Scroller | `withProjectLock`, `applyFilters`, `rankScroller`, `RANK_TRACKED_SHEETS`, `getRankScrollerOptions_` |
| `refreshAllFiltersOnly(...)` | Применяет фильтры ко всем отслеживаемым листам без сортировки и Rank Scroller | `RANK_TRACKED_SHEETS`, `applyFilters`, `getRankScrollerOptions_` |
| `refreshAllFiltersAndRanks(...)` | Обновляет фильтры всех листов, затем один раз запускает Rank Scroller | `RANK_TRACKED_SHEETS`, `applyFilters`, `rankScroller`, `getRankScrollerOptions_` |

**Наблюдения:**

- Все четыре публичные операции используют `withProjectLock()`.
- Настройки Options читаются один раз на операцию и передаются дальше в фильтры и Rank Scroller. Это сохраняет пакетное чтение и не требует повторного чтения настроек внутри каждого листа.
- `refreshAllFiltersOnly()` намеренно вызывает `applyFilters(true, ...)`: автоматическая сортировка пропускается.
- `refreshAllFiltersAndRanks()` применяет фильтры с `skipAutoSort=false`, выполняет один `SpreadsheetApp.flush()`, после чего вызывает Rank Scroller один раз для всех листов.
- `refreshFiltersAndRanks()` проверяет лист по `RANK_TRACKED_SHEETS`, а `refreshAll...` используют тот же список для обхода листов.
- В `resetFilters()` диапазон очистки задан литералом `'I1:J1'`, а не через `CONFIG.dotsFilterCell` и `CONFIG.modeFilterCell`. Это подтверждённая точка централизации, но менять её следует только после проверки всех аналогичных операций и согласования.
- Шаг трассировки `Read Options A5:A9` в `resetFilters()` не совпадает с фактическим диапазоном, который читает `getRankScrollerOptions_()` (`A5:A11`). Это только неточность диагностической подписи; на чтение данных не влияет.

### 19.2. SortOperations.gs

| Функция | Назначение | Основные зависимости |
|---|---|---|
| `manualSortByScoreDesc()` | Ручная сортировка High Score по убыванию | `runManualSortOperation_()` |
| `manualSortByScoreAsc()` | Ручная сортировка High Score по возрастанию | `runManualSortOperation_()` |
| `manualSortByDots()` | Ручная сортировка Dots A–Z | `runManualSortOperation_()` |
| `getSortRowKey_(row)` | Создаёт ключ строки C:L с нормализацией Date через timestamp | `JSON.stringify`, `Date` |
| `buildSortVisibilityQueues_(data, visibility)` | Строит очереди исходной видимости для одинаковых строк | `getSortRowKey_()` |
| `restoreSortedRowVisibility_(...)` | Сопоставляет отсортированные строки с исходной видимостью, восстанавливает show/hide и обновляет FilterState | `getSortRowKey_`, `showRowsInGroups`, `hideRowsInGroups`, `updateVisibleRowsState` |
| `runManualSortOperation_(...)` | Полный сценарий ручной сортировки без запуска `applyFilters()` | `withProjectLock`, `getTargetSheet`, `getPreviousVisibility`, `sortScenarioBlocks`, `restoreSortedRowVisibility_`, `SpreadsheetApp.flush` |

**Подтверждённый поток ручной сортировки:**

1. Получить активный целевой лист и последнюю строку.
2. Прочитать исходный диапазон C:L одним запросом.
3. Получить предыдущую видимость через `getPreviousVisibility()`.
4. Построить очереди видимости по ключу содержимого строки.
5. Передать уже прочитанные сценарии в `sortScenarioBlocks()`.
6. Выполнить `flush()` и повторно прочитать C:L.
7. Восстановить физическую видимость строк в соответствии с их исходными записями.
8. Синхронизировать `_FilterState` через `updateVisibleRowsState()`.
9. Выполнить итоговый `flush()` и показать toast.

**Важные свойства реализации:**

- Ручная сортировка не запускает `applyFilters()`.
- Видимость связывается с содержимым C:L, а не с прежним номером строки.
- Для полностью одинаковых строк используются очереди, поэтому несколько одинаковых записей могут сохранять разные значения видимости.
- `getSortRowKey_()` и `getManualRecordKey_()` решают похожие, но разные задачи: первый использует `Date.getTime()`, второй — `Date.toISOString()`. Не объединять их без отдельного анализа совместимости сохранённых ключей.
- Ошибка сопоставления строки или оставшиеся элементы очередей приводят к исключению до завершения операции.

### 19.3. FilterState.gs

| Функция | Назначение |
|---|---|
| `getFilterStateSheet()` | Получает или создаёт скрытый лист `_FilterState` |
| `getFilterStateColumns(sheet)` | Возвращает блок видимости и метаданных: Novice A:B, Intermediate D:E, Advanced G:H |
| `ensureFilterStateLayout(stateSheet, metadataValues)` | Проверяет заголовки, при необходимости мигрирует старый блок Intermediate из A:B в D:E, синхронизирует переданные метаданные и кэширует структуру |
| `getPreviousVisibility(...)` | Читает сохранённую видимость, проверяет её корректность, дополняет новые строки `true`; при непригодном состоянии использует физическую видимость листа |
| `updateVisibleRowsState(...)` | Обновляет метаданные и массив видимости, пропускает неизменившиеся записи и очищает устаревшие значения при сокращении листа |

**Схема `_FilterState`:**

| Лист | Колонка видимости | Колонка LastRow |
|---|---:|---:|
| Novice | A | B |
| Intermediate | D | E |
| Advanced | G | H |

**Подтверждённые детали реализации:**

- `FILTER_STATE_LAYOUT_CACHE` действует в пределах одного выполнения скрипта.
- `ensureFilterStateLayout()` может повторно использовать уже прочитанный массив метаданных `A1:Q2`, сокращая отдельные чтения.
- Миграция старого состояния Intermediate выполняется при наличии заголовков `Visible` / `LastRow` в A:B и отсутствии заголовка Intermediate в D1.
- `getPreviousVisibility()` считает сохранённое состояние пригодным, только если все перекрывающиеся значения — строго boolean `true` или `false`.
- Новые строки при расширении диапазона считаются видимыми.
- Если сохранённое состояние непригодно, функция читает `isRowHiddenByUser()` построчно и затем сохраняет резервное состояние.
- `updateVisibleRowsState()` отдельно сравнивает метаданные и массив видимости, чтобы не выполнять ненужные записи.

**Вопрос для последующей проверки:** при cache hit в `ensureFilterStateLayout()` функция возвращает кэшированный лист до обработки нового `metadataValues`. Если вызывающий код в рамках одного исполнения передаст свежий массив метаданных после первого вызова `ensureFilterStateLayout()`, этот массив не будет синхронизирован кэшированным путём. Нужно проверить фактические последовательности вызовов и жизненный цикл передаваемого массива; это потенциальный крайний случай, а не подтверждённая ошибка текущего runtime.

### 19.4. ManualState.gs

| Функция | Назначение |
|---|---|
| `getManualStateColumns(sheet)` | Возвращает блок ManualState: Novice J:K, Intermediate M:N, Advanced P:Q |
| `getManualRecordKey_(row)` | Создаёт стабильный ключ записи C:L, нормализуя Date в ISO и пустые значения в `null` |
| `loadManualHiddenKeyCounts_(...)` | Загружает сохранённые ключи и считает количество одинаковых записей в `Map` |
| `consumeManualHiddenKey_(row, counts)` | Проверяет наличие ручного исключения и уменьшает его счётчик |
| `saveManualHiddenRows()` | Сохраняет физически скрытые пользователем строки, исключая строки, уже скрытые фильтрами |

**Схема ManualState:**

| Лист | Колонка ключа | Колонка Count |
|---|---:|---:|
| Novice | J | K |
| Intermediate | M | N |
| Advanced | P | Q |

**Поток `saveManualHiddenRows()`:**

1. Читает C:L и определяет последнюю игровую строку по столбцу C.
2. Проверяет, что FilterState содержит актуальное состояние для этого диапазона.
3. Читает FilterState и проверяет, что все значения видимости — boolean.
4. Рассматривает только строки, которые видимы по FilterState, но физически скрыты пользователем (`isRowHiddenByUser`).
5. Сохраняет ключи строк и их количество в соответствующем блоке ManualState.
6. Очищает старые ключи, если новый список короче.

ManualState хранит идентификаторы записей по C:L, а не номера строк. Повторяющиеся одинаковые записи учитываются через частотные счётчики в `Map`.

В предоставленной версии CONFIG `perfModeCell` равен `A12`, а `perfDefaultMode` — `DEBUG`. Следовательно, эти два параметра CONFIG имеют подтверждённых потребителей и не являются неиспользуемыми.

### 19.7. Lock Manager 2.1

| Функция | Назначение |
|---|---|
| `withProjectLock(callback, parentTrace)` | Получает ScriptLock, выполняет callback, освобождает lock, фиксирует этапы и корректно пробрасывает ошибку |

**Подтверждённый порядок:**

1. Использует переданную родительскую трассировку либо создаёт собственную.
2. Вызывает `LockService.getScriptLock()` и `waitLock(30000)`.
3. Записывает `LOCK_ACQUIRED` или `LOCK_WAIT_FAILED` и длительность ожидания.
4. При успешном lock выполняет callback и фиксирует `Locked callback execution`.
5. Освобождает lock и фиксирует `Lock release`.
6. Если трассировка создана внутри Lock Manager, завершает её самостоятельно.
7. После очистки повторно выбрасывает сохранённую исходную ошибку.

Если callback уже завершился ошибкой, ошибка освобождения lock добавляется в metadata и не заменяет исходную ошибку. Если исходной ошибки нет, ошибка освобождения получает статус `LOCK_RELEASE_ERROR`.

В ранних исторических заметках упоминалось чтение режима диагностики из `A10`. В актуальном предоставленном CONFIG поле `perfModeCell` задано как `A12`, и Tracer использует именно это поле. При этом `getRankScrollerOptions_()` читает `Options!A5:A11`, где A10 и A11 относятся к настройкам Rank Scroller. Поэтому текущая конфигурация A12 разделяет настройки корректно.

## 22. Замечания аудита и кандидаты на дальнейшую проверку

Это не список подтверждённых ошибок. Это точки, которые следует проверить перед изменениями.

1. **Единый источник списка игровых листов.** `RANK_TRACKED_SHEETS` используется операциями и триггерами, тогда как Rank Scroller получает список из `CONFIG.rankScroller.sheets`. Два списка должны оставаться синхронными. Возможный вариант — вычисляемый helper на основе `Object.keys(CONFIG.rankScroller.sheets)`, но внедрять его следует после глобального поиска.
2. **Литералы координат.** `resetFilters()` очищает `'I1:J1'`, хотя координаты фильтров уже есть в CONFIG. Проверить и другие операции на аналогичные литералы.
3. **Диагностическая подпись диапазона.** `resetFilters()` пишет `Read Options A5:A9`, хотя функция читает A5:A11. Исправление подписи безопаснее, чем изменение логики чтения.
4. **Кэш FilterState.** Проверить сценарий повторного вызова `ensureFilterStateLayout()` с новым `metadataValues` после cache hit.
5. **Lock Manager и вложенные lock-вызовы.** Проверить глобально, не вызывает ли callback функции, которые повторно пытаются получить тот же ScriptLock. В предоставленных цепочках такого вложенного получения не установлено.
6. **`perfLockWait_()`.** Функция присутствует, но в предоставленной версии Lock Manager не вызывается; Lock Manager сам пишет `LOCK_ACQUIRED` и `Lock wait`. Кандидат на удаление только после поиска по всему проекту.
7. **Публичные точки входа ручной сортировки.** Проверить соответствие названий функций пунктам меню в `onOpen()` и убедиться, что нет старых альтернативных обработчиков.
8. **Проверка структуры ManualState.** `ensureFilterStateLayout()` проверяет A:H, а ManualState самостоятельно пишет J:Q. При дальнейшем изменении структуры служебного листа нужно сохранять независимость этих областей.

## 24. Сверка FilterVisibility.gs и исторических снимков Filters.gs

### 24.1. Подтверждённый отдельный модуль

В загруженном полном `FilterVisibility.gs` присутствуют:

| Функция | Назначение | Зависимости |
|---|---|---|
| `showAllDataRows(sheet, knownLastRow, stateSnapshot)` | Показывает строки с названием сценария, скрывает пустые, обновляет FilterState и при необходимости заполняет snapshot | `CONFIG`, `showRowsInGroups`, `hideRowsInGroups`, `ensureFilterStateLayout`, `getFilterStateColumns`, `updateVisibleRowsState` |
| `updateRowsVisibility(sheet, previousVisibility, newVisibility)` | Меняет физическую видимость только изменившихся строк | `CONFIG.firstRow`, `showRowsInGroups`, `hideRowsInGroups` |
| `resolvePreviousPhysicalVisibility_(...)` | Определяет предыдущую физическую видимость с учётом ManualState | `CONFIG.firstRow`, `filterPerfStep_` |
| `saveFilterVisibility_(...)` | Применяет физическую видимость и сохраняет только FilterState | `updateRowsVisibility`, `updateVisibleRowsState`, `filterPerfStep_` |

### 24.2. Карта вызовов

```text
showAllDataRows
  ├─ showRowsInGroups
  ├─ hideRowsInGroups
  └─ updateVisibleRowsState

resolvePreviousPhysicalVisibility_
  └─ filterPerfStep_
      ├─ logFilterTiming
      └─ triggerPerfStep_

saveFilterVisibility_
  ├─ updateRowsVisibility
  │   ├─ showRowsInGroups
  │   └─ hideRowsInGroups
  └─ updateVisibleRowsState
```

### 24.3. Наблюдения

1. `showAllDataRows()` читает только столбец сценария. Для определения пустых строк этого достаточно.
2. При переданном `stateSnapshot` функция вызывает `ensureFilterStateLayout()`, получает блок колонок и затем сохраняет snapshot: `stateSheet`, `columns`, `metadata`, `previousVisibility`.
3. `showAllDataRows()` передаёт `stateSheet` в `updateVisibleRowsState()`, но не передаёт `metadata`. Поэтому метаданные читаются внутри `updateVisibleRowsState()` отдельным обращением.
4. `updateRowsVisibility()` предполагает, что `previousVisibility` и `newVisibility` соответствуют одному диапазону и имеют согласованную длину; отдельной проверки длины нет.
5. `resolvePreviousPhysicalVisibility_()` сверяет физическое состояние только для строк из `manuallyHiddenRows`. Для остальных строк источником предыдущей фильтрационной видимости является FilterState.
6. `saveFilterVisibility_()` сохраняет `newFilterVisibility`, а не итоговую физическую `newVisibility`. Это сохраняет разделение FilterState и ManualState.

### 24.4. Сопоставление с историческим Filters.gs

В загруженных снимках `Вставленный текст(20261110-055143).txt` и `Вставленный текст(20261110-051533).txt` находится более ранняя монолитная реализация `applyFilters()`. В ней вычисление предыдущей физической видимости, вызов `updateRowsVisibility()` и сохранение FilterState находятся непосредственно внутри `applyFilters()`.

В отдельном `FilterVisibility.gs` эти обязанности вынесены в `resolvePreviousPhysicalVisibility_()` и `saveFilterVisibility_()`.

**Вывод:** исторический монолитный `Filters.gs` нельзя считать доказательством дублирования функций в текущей модульной архитектуре. Для проверки актуальных вызовов нужен текущий отдельный `Filters.gs`.

### 24.5. Кандидаты на проверку

- Убедиться, что актуальный `Filters.gs` вызывает `resolvePreviousPhysicalVisibility_()` и `saveFilterVisibility_()`, а не содержит параллельную inline-реализацию.
- Проверить, где формируется и используется `stateSnapshot`, и совпадает ли его контракт у вызывающих функций.
- Проверить, что все callers передают отсортированные массивы строк в `showRowsInGroups()` и `hideRowsInGroups()`.
- Не удалять `updateRowsVisibility()` или `saveFilterVisibility_()` без глобального поиска вызовов.

### 27.3. Состояния остаются независимыми

`buildFilterVisibility_()` формирует два самостоятельных набора:

- `filterRowsToHide` — строки, скрытые фильтрами или из-за пустого названия сценария;
- `manualRowsToHide` — строки, скрытые по ключам ManualState.

`filterVisibility` строится только на основании `filterRowsToHide`. Поэтому ручное скрытие не записывается как фильтрационное.

Итоговая физическая видимость в `applyFilters()`:

```javascript
filterVisible && !manualRowsToHide.has(sheetRow)
```

`saveFilterVisibility_()` получает отдельно `newVisibility` и `newFilterVisibility`, применяет первую физически, а в FilterState записывает вторую. Это соответствует архитектурному разделению FilterState и ManualState.

### 27.4. TOP рассчитывается после Dots и ManualState

Порядок в `buildFilterVisibility_()`:

1. Пустая строка сценария добавляется в `filterRowsToHide`.
2. Проверяется ключ ManualState. Совпавшая строка добавляется в `manualRowsToHide` и исключается из дальнейшей обработки.
3. Проверяется Dots.
4. Проверяется High Score и настройка `hideEmptyScores`.
5. Оставшиеся строки группируются по названию сценария.
6. В каждой группе результаты сортируются по Score по убыванию; при равенстве Score сохраняется порядок строк листа.
7. Всё после TOP-N добавляется в `filterRowsToHide`.

Следовательно, ручные исключения и строки, не прошедшие Dots, не участвуют в TOP. Строки с пустым/некорректным Score не попадают в TOP-группу; при выключенном `hideEmptyScores` они остаются видимыми, если не скрыты другим правилом.

## 28. Проверка производительности и контрактов фильтров

### 28.1. Чтение игровых данных

`readFilterInputData_()` читает один прямоугольный диапазон:

- начало: строка 1, столбец `CONFIG.scenarioCol` (C);
- высота: `sheetLastRow`;
- ширина: `CONFIG.sortWidth` (10 столбцов, C:L).

Из первой строки извлекаются настройки фильтров:
- Dots — индекс `CONFIG.dotsCol - CONFIG.scenarioCol`, то есть I;
- Mode — следующий столбец, то есть J.

Игровой массив начинается с `CONFIG.firstRow`, то есть со строки 3. Таким образом, один `getValues()` заменяет отдельные чтения игровых данных и ячеек I1/J1.

### 28.2. Повторное использование knownFilterState

`prepareFilterState_()` принимает snapshot только если одновременно присутствуют:
- `stateSheet`;
- `columns`;
- массив `metadata`;
- массив `previousVisibility` длиной не меньше `numRows`.

При пригодном snapshot повторно используются `stateSheet`, `columns`, `metadata` и предыдущая видимость. При этом диапазон A1:Q2 всё равно читается одним запросом, поскольку из него извлекаются метаданные ManualState. Это не случайное дублирование чтения игровых данных, а объединённое чтение служебных метаданных.

### 28.3. Группировка операций видимости

`hideRowsInGroups()` самостоятельно сортирует номера строк перед группировкой. `showRowsInGroups()` сортировки не выполняет и предполагает, что входной массив уже упорядочен по возрастанию.

В текущем показанном потоке:
- `updateRowsVisibility()` проходит `newVisibility` по индексам сверху вниз и формирует возрастающий `rowsToShow`;
- `showAllDataRows()` также строит строки в порядке обхода массива сценариев.

Поэтому показанные callers соблюдают контракт. Если в будущем `showRowsInGroups()` будет вызываться напрямую с произвольным массивом, сортировку следует выполнить до вызова либо документировать требование к порядку.

### 28.4. Замечания, не требующие немедленного изменения

1. `getLastScenarioRow(sheet)` — совместимая, но более затратная точка входа: она самостоятельно читает C:I. В основном `applyFilters()` используется более эффективный `getLastScenarioRowFromData(inputData.data)`, который повторно не обращается к листу.
2. `prepareFilterState_()` при наличии snapshot всё равно читает A1:Q2, но не повторно загружает игровую таблицу. Это необходимо для подготовки ManualState metadata.
3. `updateRowsVisibility()` не проверяет равенство длин массивов. Внутренний caller формирует их из одного `newVisibility` и ожидает соответствующую предыдущую видимость. Дополнительная проверка может быть полезна как защита контракта, но это отдельное изменение.
4. `showRowsInGroups()` не проверяет сортировку и уникальность входных номеров. Текущие известные callers передают возрастающий список; при добавлении новых callers это требование нужно соблюдать.
5. `knownFilterState` не проверяется на принадлежность конкретному листу. Если snapshot может передаваться между листами, вызывающий код должен гарантировать корректную привязку. Если snapshot создаётся и используется в рамках одной операции для одного листа, текущая проверка достаточна для заявленного сценария.

## 30. Проверки Rank Scroller и потенциальные граничные условия

### 30.1. Чтение Energy

`readRankScrollerSheetData_()` читает одну строку, начиная с `config.energyColumn` (M), шириной `config.thresholdColumns + 1`. Первый элемент — Energy, остальные — EnergyThreshold.

Для переданной CONFIG:
- Novice: M:AB (Energy + 15 thresholds);
- Intermediate: M:AC (Energy + 16 thresholds);
- Advanced: M:AC (Energy + 16 thresholds).

Energy преобразуется через `parseFloat()` и корректируется:

```javascript
energyValue -= 20 * colBehind;
```

### 30.2. Ранний выход

Обновление пропускается только если:
- Energy не изменилась;
- настройки не изменились;
- `forceUpdate` выключен.

Если предыдущее значение отсутствует или не преобразуется в число, `parseFloat()` возвращает `NaN`; сравнение с текущей Energy даст `true`, поэтому обновление будет выполнено. Это безопасное поведение для первичной инициализации.

### 30.3. Calculator

Алгоритм:
1. Если Energy ниже первого порога — выбирает первую колонку.
2. Иначе ищет интервал `[threshold[j], threshold[j+1])`.
3. Затем отдельно проверяет `specialCaseIndex = totalColumns - visibleColumns`. Если Energy достигла этого порога, целевая колонка переопределяется на начало последнего окна.

Последняя проверка намеренно может переопределить найденную ранее колонку. Это явно отмечено в комментарии исходника как сохранение существующего поведения.

### 30.4. Rank Tiers

При `rankTiersValue === false` функция показывает только значения EnergyThreshold, которые:
- имеют тип JavaScript `number`;
- делятся на 100 без остатка.

Соседние подходящие значения объединяются в группы. Строковые числовые значения, например `"500"`, текущая реализация не показывает, потому что использует строгую проверку `typeof value === 'number'`.

### 30.5. Валидация

- `showRankScrollerColumns_()` проверяет границы и типы аргументов перед изменением колонок.
- `showRankScrollerTierColumns_()` проверяет лист, целочисленные координаты, положительную ширину и достаточную длину `energyValues`.
- `calculateRankScrollerTargetColumn_()` полагается на вызывающий Engine при проверке `visibleColumns`; самостоятельной полной валидации аргументов в Calculator нет.

Это не выявленные runtime-ошибки, а контракты между слоями. При сохранении текущей архитектуры Engine остаётся ответственным за предварительную проверку `visibleColumns`.

## 34. Дополнительные замечания по реализации

### 34.1. `showRowsInGroups()` и порядок строк

`showRowsInGroups()` объединяет соседние строки, но не сортирует входной массив.

В известных путях вызова порядок обеспечивается:
- `updateRowsVisibility()` формирует `rowsToShow` обходом `newVisibility` от первого элемента к последнему;
- `showAllDataRows()` формирует `rowsToShow` обходом `visibility` сверху вниз.

Поэтому для этих callers номера возрастают. `hideRowsInGroups()` в отличие от `showRowsInGroups()` сортирует входной Set самостоятельно.

### 34.2. `showAllDataRows()` и snapshot

При переданном `stateSnapshot` функция:
1. вызывает `ensureFilterStateLayout()`;
2. получает блок колонок FilterState;
3. применяет физическую видимость;
4. вызывает `updateVisibleRowsState()`;
5. формирует snapshot с метаданными и копией видимости.

`updateVisibleRowsState()` в этом пути получает `stateSheet`, но не готовый `metadata`, поэтому самостоятельно читает метаданные. Это дополнительное чтение, но не ошибка корректности. Возможная оптимизация — передавать актуальные metadata, если вызывающий код уже их прочитал.

### 34.3. `knownFilterState` и привязка к листу

`prepareFilterState_()` проверяет наличие полей snapshot и длину `previousVisibility`, но не сверяет, что snapshot относится к тому же листу, который передан в `applyFilters()`.

Если snapshot создаётся и используется в пределах одной операции для одного листа, это допустимый контракт. Если snapshot может переиспользоваться между листами, следует добавить идентификатор листа и проверять его. До выяснения всех callers менять структуру snapshot не следует.

### 34.4. `FilterState` metadata и единое чтение

`prepareFilterState_()` читает A1:Q2 одним запросом, затем извлекает из массива метаданные FilterState и ManualState. Это целенаправленная оптимизация, а не лишнее повторное чтение. При переданном `knownFilterState` повторно используется FilterState snapshot, но A1:Q2 всё равно читается для актуальных метаданных ManualState.

### 34.5. `RankScrollerCalculator` и проверка параметров

`calculateRankScrollerTargetColumn_()` не выполняет полную валидацию входных параметров. В текущем потоке `RankScrollerEngine.updateRankScrollerVisibility_()` проверяет `visibleColumns` перед вызовом Calculator в режиме Rank Tiers. Это разделение ответственности допустимо, но самостоятельные вызовы Calculator должны передавать валидные аргументы.
